Mundipagg Design System / Color Refactor

Turning dark mode from an inverted skin into a color system.

In 2019, dark mode was not yet the default expectation it is today. Mundipagg already had one, but it behaved like an inverted light theme: visually heavy, hard to scan, and not comfortable enough for developers and clients who used dashboards all day.

Timeline: late 2019 Role: Product Designer / UI Specialist Scope: design-system color refactor

The short version

We had a very limited palette, and dark mode was treated like the inverse of light mode. That made the product look darker, but not calmer. The interface still strained vision because depth, surfaces, text and interactive states were not separated into meaningful roles.

My work was to make the case for a color refactor, define the new color logic with design-system developers, and help leadership see why this was not polish. It was infrastructure.

Problem

A limited palette could not support a serious dark mode.

What we had

Design Principle

Dark mode is not light mode with the values flipped.

Inspired by Refactoring UI's guidance on depth cues, I treated dark mode as its own environment: closer surfaces become slightly lighter, text needs calibrated contrast, and shadows cannot carry the same visual load they carry on light backgrounds.

The refactor

The redesign expanded the palette and reorganized it by role. Instead of asking one gray or one brand color to solve every case, we separated background colors, surface colors, font colors, semantic states, and action colors across light and dark themes.

This made the system easier to implement and safer to evolve. It also gave developers a clearer language for discussing UI decisions.

Expanded palette

From inverted colors to a robust light and dark system.

The first dark mode leaned on a small set of inverted neutrals. The refactor created separate ramps for background, surface, border, disabled, and font colors, so each theme could carry depth and contrast without straining the eye.

Making the case for refactoring

The hardest part was not choosing better colors. It was brokering alignment with development leadership that a color refactor would pay off.

I framed the work as a product-quality investment: fewer accessibility problems, clearer implementation rules, and a dark mode that developers would actually want to use every day.

Objective

WCAG compliant

Color combinations were tested and adjusted until key UI text and controls met accessibility standards.

Subjective

More comfortable

Testing and surveys showed clients were pleased with the outcome.

Internal adoption

Developers liked it

The strongest signal came from developers, who noticed and complimented the new dark mode in daily use.

Light mode

The refactor improved the original theme too.

Even though dark mode motivated the work, separating chromatic families also made light mode cleaner. The new palette created better surface hierarchy and a more comfortable dashboard without relying on heavy contrast everywhere.

After

A color system that could scale with the product.

The result was not just a prettier dashboard. It was a more usable interface, a more maintainable design system, and a clearer collaboration model between design and engineering.
